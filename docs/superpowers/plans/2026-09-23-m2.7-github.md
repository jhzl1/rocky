# M2.7 GitHub Pull Request Panel Implementation Plan

**Status: done**, merged into `development` on 2026-09-24 with M2.6 brought in first; 391 tests pass. The manual checklist on a throwaway repository is still open: `docs/superpowers/m2.7-verification.md`.

> **Execution:** task by task. Tests are written with each change and run once, in Task 15 (global rule `## Tests` in `~/.claude/CLAUDE.md`). Build once, at the end of the tasks (the rule the user gave in M2.5), and commit only when the user asks; each task's commit line is the message to use then. This plan gives decisions, files, public interfaces, required behavior and the tests to write. It does not carry the code: the implementer writes it.

**Goal:** Inside a workspace, see its pull request the way Conductor shows it: a right panel whose header, tinted by the pull request's state, offers one next action, and a Checks tab with the editable title and body, Git status, deployments, checks and review comments. Creating the pull request, committing, fixing CI, resolving conflicts and answering comments go to the agent as prompts; Rocky itself reads GitHub, merges, marks ready, pulls and pushes. Each repository works with its own GitHub account, and every process of its workspaces gets that account's token.

**Visual and behavioral source of truth:** `docs/superpowers/design/2026-09-23-m2.7-github.html`, written by dev-2. Open it in a browser. The mock's data, GitHub calls and agent replies are JavaScript stand-ins: do not port them. What the plan needs and the HTML does not say is under "Open questions", not decided here.

## Decisions

Taken with the user on 2026-09-23:

- **M2.7 is its own milestone and lands before M3.**
- **The agent creates and fixes the pull request, as in Conductor.** "El problema no es quien crea el PR, sino la visualización": Rocky's job is to show the pull request and to hand the agent the right prompt.
- **Scope:** pull request state, checks and merge; fix CI, resolve conflicts and send GitHub review comments to the agent. Notifications are not part of M2.7 (M2.5 built them).
- **The repository's account reaches agents, terminals and scripts now** (`ENV-01`, moved from M4).
- **All GitHub reads over `URLSession`** on Rocky's schedule, never a `gh` process per refresh (`PR-07`).
- **Merge offers the methods the repository allows** (`PR-05`; Conductor uses only the first). A pick lasts for the workspace until Rocky quits and is never stored.
- **Agent buttons are disabled while the selected conversation's turn runs** ("The agent is working"), and never go into M2.5's message queue (`AGT-00`).

Taken in this plan. Change them here, not during implementation:

- **`PullRequestMonitor` owns the refresh loop,** apart from `AppModel`, with an injected loader, clock and sleep so the schedule is testable. `AppModel` forwards its triggers and builds the loader.
- **The base** is the pull request's `baseRefName` once one exists, else the workspace's `baseRef` as a branch name (`WorkspaceContext.branchName(fromBaseRef:)`). It fills every "development" of the prompts, the compare query and the compare URL (no `baseRef`: Open question 9).
- **Lookups use the live branch** (`# branch.head` of the status), not `Workspace.branch`, so an agent that renames the branch keeps its pull request.
- **The local `git status` runs on PR-07's event triggers only** (selection, key window, a Rocky action, a turn's end, the refresh button), never on the schedule's ticks: spec Section 1 forbids polling Git.
- **Without an upstream,** "ahead" counts the commits on no `origin` branch and "behind" is 0, so GST-03's `push -u origin HEAD` has a count to show.
- **`environment(for:)` stays synchronous** and reads the cached token. Every place that starts a process awaits `AppModel.prepareEnvironment(for:)` first; `openTerminal` becomes `async` for it.
- **Rocky's own `gh` runs** (`gh auth status --json hosts`, `gh auth token --user`) get the login environment without `GH_TOKEN` and `GITHUB_TOKEN`, or `gh` would report the variable's account instead of the keyring's. Never `--show-token`.
- **SSH alias hosts** (`github-celes`) are resolved once per repository per launch with `ssh -G <host>`; the remote counts as GitHub when its `hostname` is `github.com`.
- **One ephemeral `URLSession`** for GitHub: no response or credential reaches the disk cache.
- **The pull request columns are saved by a column-only update,** never `update(_: Workspace)` from a stale copy, which would undo a rename.
- **"Added to chat" marks live in memory;** hidden comment ids are stored (`PR-07` lists only those). Unsaved title and body drafts live in the monitor, per workspace, in memory.
- **A toast** is new in RockyUI (`GST-02`, `ERR-01`, `SET-01` need one), drawn as the mock's `.toast`.
- **The account picker is Rocky's menu.** The repository settings sheet is its own window, so it gets its own `MenuPresenter` and `MenuHost`; its existing `Picker`s stay as they are.
- **The tab row is a list of `RightPanelTab`** with one case in M2.7; M3 adds `.changes` (`CHG-01`) before `.checks`. The selected tab per workspace is kept in `AppModel`, in memory.
- **The panel's width and range do not zoom,** like the terminal panel's heights (M2.5 record).
- **Out of M2.7** (`OUT-30`): a Rocky form to create the pull request, the Changes tab (M3), All files, Conductor's Desktop, Summary and Review, Automerge, Approve and merge queue actions, "Continue" after merge, Vercel's "View logs", resolving or editing review threads (not planned), `GIT_AUTHOR_*`, SSH keys and the Claude instance per account (M4).

## Open questions

All fourteen were resolved by the designer on 2026-09-23, and the design HTML carries the answers. Where an answer
differs from the proposal first written here, the HTML wins:
1. `queued_to_merge`: only `mergeQueueEntry` counts (auto-merge is `OUT-30`). `AWAITING_CHECKS` → "Merge queue
   checks pending", `UNMERGEABLE` → "Merge queue blocked", `LOCKED` → "Merge queue locked", anything else →
   "Queued to merge".
2. Optional checks: failed checks give `checks_failing` only when `mergeStateStatus` is not `UNSTABLE`. With
   `UNSTABLE`, the state is `ready_to_merge` and the label reads "N optional checks failed".
3. The full mapping is in `HDR-02`:
   - `CLEAN`, `UNSTABLE`, `HAS_HOOKS` → `ready_to_merge`
   - `BLOCKED` → `review_required` when a review is required, else `blocked`
   - `UNKNOWN` → `loading_pr`
   - `BEHIND` → `unable_to_merge`, "Unable to merge · behind <base>"
4. Incompatible with the remote:
   - `PR-01` gains `headRefOid`. When it differs from `refs/remotes/origin/<branch>`, Rocky runs `git fetch origin
     <branch>` once.
   - Incompatible means ahead and behind the upstream at once.
   - "Remote branch was rebased" means the tracking ref's last reflog entry contains "forced-update".
   - `pull` is shown when the branch is only behind, `push` when it is only ahead.
5. "PR info unavailable": origin is not a GitHub remote, or GitHub answers `NOT_FOUND` (`ERR-01`).
6. "View checks" opens `<pull request url>/checks` in the browser.
7. The extra lines of Fix errors: as proposed, in `AGT-03`.
8. Comments include their replies and the review bodies:
   - A thread's replies follow its first comment as `> login: text`, with `> ` on every line.
   - `latestReviews(first: 20) { author { login } state body }`: each reviewer's latest changes-requested review
     with a body becomes the item "N. ana (review)" and a Comments row located at "review".
9. `defaultBranchRef { name }` is in `PR-01`; the base is `baseRef`, else `defaultBranchRef.name`.
10. Layer order follows spec Section 3: login < repository variables < account variables, so the account's
    `GH_TOKEN` wins. `ENV-01` was corrected.
11. `SET-01` goes in a new "GitHub" section after "Terminal".
12. The picker's default entry reads "Automatic (jhzl1)"; choosing it stores nil.
13. Archive from the header asks nothing when the worktree is clean. With uncommitted or untracked files it asks
    "tokyo has 3 uncommitted changes. Archive anyway?" (Cancel / Archive). `SET-01` skips a dirty worktree and
    says "tokyo merged but has uncommitted changes; not archived".
14. A merged pull request's Git status is only "Merged into development", with a `merged` dot and no action.

## Global constraints

- macOS 15 minimum, Swift 6 language mode. No new Swift package. The GitHub and Vercel marks are Simple Icons SVGs (CC0), like the agents' logos.
- **Zoom:** text through `Font.rocky`, text- and icon-holding sizes through `Zoom.shared(_:)`, colors from `Theme` tokens.
- **Energy (spec Section 1, `PR-07`):**
  - GitHub over `URLSession` GraphQL and REST with the repository account's token; never a `gh` process per refresh.
  - Tokens from `gh auth token --user <login>`, once per launch, on first need, in memory only; never stored, logged or put in a URL or an error message.
  - Polling only for the selected workspace while the window is key, on the `PollSchedule` backoff.
  - No disk-polling timers: `git` runs only on event triggers. `gh` runs only for the account list and the tokens; `git remote get-url` and `ssh -G` once per repository per launch.
- Menus: Rocky's own (`MenuButton`, `MenuItem`, `MenuDivider`); no SwiftUI `Menu` or `.contextMenu`.
- Git runs in the worktree with the workspace environment plus `GIT_TERMINAL_PROMPT=0` and `ssh -o BatchMode=yes`, off the main actor. Rocky never force-pushes, never creates a merge commit, never deletes a remote branch, never passes `--no-verify`.
- All code, comments, identifiers and UI copy in English. Commits: Conventional Commits, no AI attribution line. Shell: `bat`, `eza`, `rg`, `fd`, `sd`.
- Manual tests of the pull request flow only on throwaway personal repositories, never a work repository.

### Task 1: Remotes and GitHub accounts

**Requirements:** `ACC-01` (accounts, binding default, owner and name).
**Files:** `Sources/RockyKit/GitHub/RemoteURL.swift` (new), `Sources/RockyKit/GitHub/GitHubAccounts.swift` (new), `Tests/RockyKitTests/RemoteURLTests.swift` (new), `Tests/RockyKitTests/GitHubAccountsTests.swift` (new).

```
public struct RemoteURL: Equatable, Sendable {
  public let host: String; public let owner: String; public let name: String; public let isSSH: Bool
  public static func parse(_ url: String) -> RemoteURL?          // https, ssh://, git@host:o/n(.git)
}
public struct GitHubRepository: Hashable, Sendable { public let owner: String; public let name: String }
public enum GitHubRemote { public static func repository(from: RemoteURL, sshHostName: (String) throws -> String?) rethrows -> GitHubRepository? }
@MainActor public final class GitHubAccounts {
  public init(runGH: @escaping @Sendable ([String]) throws -> String)
  public func logins() async throws -> [String]                  // gh auth status --json hosts --hostname github.com
  public func activeLogin() async throws -> String?
  public func token(for login: String) async throws -> String    // gh auth token --user <login> --hostname github.com
  public func cachedToken(for login: String) -> String?
  public static func defaultLogin(owner: String, logins: [String], active: String?) -> String?
}
public enum GitHubAccountError: Error, CustomStringConvertible { case ghNotFound, notLoggedIn(String?), failed(String) }
```

It must:
- Fetch a login's token once per launch; concurrent callers share one `gh` run; a failure is not cached, so Retry (`ERR-01`) can try again after `gh auth login`.
- `defaultLogin`: the login equal to the owner (case-insensitive), else the active one.
- Accept `github.com` as is; any other SSH host is an alias, accepted when `sshHostName` (backed by `ssh -G`) answers `github.com`; an https host other than `github.com` is not GitHub.
- Never pass `--show-token`; an error's text is built from the exit status and stderr only, and suggests `gh auth login --hostname github.com`.

Tests:
- `RemoteURLTests`: https with and without `.git`; `git@github.com:o/n.git`; `ssh://git@github.com/o/n.git`; `git@github-celes:o/n.git` and `git@github.com-personal:o/n.git` resolved through a stub; a GitLab remote rejected; garbage → nil.

## Known risks

- **GraphQL names are written from the HTML and memory.** Task 2 checks each against GitHub's schema (introspection with the user's token, or the GraphQL reference): `updatePullRequest`, `markPullRequestReadyForReview`, `mergePullRequest` and its `mergeMethod` enum, `statusCheckRollup.contexts` with `CheckRun` (`checkSuite.workflowRun.databaseId`) and `StatusContext`, `deployments(orderBy:)` with `latestStatus.environmentUrl`, `reviewThreads` (`isOutdated`, `line`), `viewerDefaultMergeMethod`, `squashMergeAllowed`, `rebaseMergeAllowed`, `mergeCommitAllowed`, `canBeRebased`, `mergeQueueEntry`, `autoMergeRequest`, and `Ref.compare(headRef:)` with which way `aheadBy` and `behindBy` count.
- **The REST rerun endpoint** (`POST …/actions/runs/{run_id}/rerun-failed-jobs`) may need a scope `gh`'s token lacks. Check `gh auth status` lists `workflow` and `repo`, and call it once on the throwaway repository before Task 9.
- **GraphQL rate limits per account** (5,000 points an hour per user, each account its own budget). Add `rateLimit { cost remaining }` to the query once during Task 2's check: at 30 s the selected workspace makes 120 queries an hour. A secondary limit shows as "Couldn't load PR info" and the schedule's next tick retries.
- **The agent's `gh` honoring `GH_TOKEN` over the keyring's active account.** M0 checked it with `git ls-remote` only. Manual item 2 settles it.
- **`git push` from the agent over ssh:** the token does not apply, the key does, and both accounts use ssh. Manual item 4 shows which key answers; a wrong one is M4's.
- **Job logs are large** (`AGT-03` saves them under `Application Support/Rocky/ci-logs`). A log goes to a temporary file and only its last 1000 lines are read, from the end; its redirect must not carry `Authorization` to the blob host (pinned by `GitHubClientTests`). Check with the biggest failing job on the throwaway repository and watch Rocky's memory.
- **⌘⇧G is the system's Find Previous** in text views (and M3's editor will have a find bar). Check the Edit menu of the running app and that ⌘⇧G in the message box toggles the panel.
- **Narrow windows:** sidebar, conversation and a 280 pt panel. Check the window's minimum width keeps the conversation readable.
- **"Behind by N" is as fresh as the last fetch:** Rocky never fetches on a timer (`GST-01`), so it changes after the agent's or `GST-02`'s fetch. Accepted.

    `AppModel`, `GitHubAccounts` and `GitFixture`, and from the synchronous tests of `GitBranchServiceTests`,
    `WorktreeServiceTests`, `WorktreeLinkerTests` and `EnvironmentTests`.
  - With all 14 threads waiting in a syscall, macOS runs no default-QoS Dispatch work. That includes `DispatchIO`,
    which SwiftTerm's `LocalProcess` reads every pseudo-terminal with. In a probe, a `DispatchIO` read on a
    pseudo-terminal never completed with 14 blocked threads and took 0.1 ms with 13. Logging `LocalProcess` during a
    full run showed no read for any session for 1.2 to 1.5 s, while exit events kept arriving on the main queue.
  - The kernel drops what a pseudo-terminal still holds 0.6 s after its shell exits unread (measured with `forkpty`:
    `waitpid` took 0.6 s, then the read got nothing). When the reads resumed, the failing sessions got only EOF.

  Fix: `BlockingWorkExecutor` (in `ProcessRunner.swift`) runs each job on a thread of its own. `Task.blocking`
  replaces `Task.detached` for every blocking call in `AppModel` and `GitHubAccounts`, the `GitFixture` helpers use
  it, and the four synchronous git suites run on it through the `.blockingWork` trait. Rocky had the same exposure: 14
  git or gh calls in flight at once stopped the output of every terminal. `waitForOutput` is back to 3 s, and a full
  run takes 1.8 s instead of 11 s. Not changed: a terminal's shell inherits every descriptor Rocky has open, because
  Foundation's pipes and the pseudo-terminal masters are not close-on-exec and SwiftTerm closes none before
  `execve`; these failures did not need it. Tests: `PTYSessionTests` in the full run.
- **2026-09-24, `swift test --no-parallel` hung: `Process.waitUntilExit()` missed the agent's exit.** A real bug, not
  a test assumption. `ACPConnection.finish()` called `waitUntilExit()` after the agent closed its stdout, and
  sometimes it never returned. In the hung process the agent was gone and `isRunning` was already false, yet the
  thread still slept in `waitUntilExit`'s run loop, holding the connection's actor; a serial run of
  `ChatSessionModelTests` alone hung on its second try, twice. In Rocky it would leave a chat whose agent exited
  stuck for good. A standalone copy of `finish()` hung 3 times in 38 tries, and 0 times in 300 with
  `terminationHandler`. Fix: `ACPConnection` finishes when its `terminationHandler` (set before `run()`) fires, and
  `ProcessRunner.run` waits on its `terminationHandler`; RockyKit has no `waitUntilExit()` left. Tests:
  `ChatSessionModelTests` and `ACPConnectionTests`, in the serial run.
- **2026-09-24, a Stop right after a start sends SIGTERM.** `PTYSession.stop()` signalled the process group `-pid`,
  which exists only once the child has called `setsid()`. Right after `forkpty`, `kill(-pid)` failed with `ESRCH` in
  294 of 300 tries, so such a Stop waited out the grace period and ended in SIGKILL. It showed once the full run got
  fast: `AppModelProcessTests.nonconcurrentRunStopsTheOtherWorkspacesRun` got signal 9. `stop()` now signals the
  child alone while its group does not exist. Test: `PTYSessionTests.stopRightAfterStartSendsTERM`.

- **2026-09-24, text selection after switching conversation tabs (user report).** With two tabs, going to the second
  and back to the first left the first's text unselectable (nothing highlighted) until the window lost and regained
  focus. Textual's `NSTextInteractionView` takes its hit areas (`exclusionRects`) and model in `updateNSView`, and a
  conversation created while the window was already key kept stale ones; a window focus change updates every view,
  which is why it recovered. `ChatView` now changes an environment value (`selectionRefresh`) 150 ms after it
  appears, which updates those overlays the same way. A hypothesis supported by the code and the symptom, checked by
  the user in the app.
