## Decisions

1. **The picker is a panel like Quick Open, not a menu.** `GHL-02` needs a search field, tabs, rows with states and
   keys, and `MenuPresenter` handles only Esc. It opens above the message box, in Quick Open's look, with its own
   presenter and key monitor. `ChatView`'s monitor yields to it, as it yields to Quick Open.
2. **GitHub goes through public `AppModel` methods.** RockyUI never holds a `GitHubClient`. `AppModel` gains a
   `GitHubLinks` API:
   - the link state for a workspace (`.unavailable(reason)` / `.available`, from the repository and account lookups
     `ACC-01` already makes, resolved once, asynchronously);
   - `issues`, `pullRequests` and `branches` pages;
   - `search(query:tab:)`;
   - `issue(number:)` and `pullRequest(number:)` in full.
   
   New queries live in `GitHubClient.swift` beside the others. `Wire.check` maps NOT_FOUND on
   `["repository","issue"]` and `["repository","pullRequest"]` to `.notFound`. Cancelling is the caller's `Task`
   cancellation, and a cancelled request's `URLError(.cancelled)` is dropped, never shown.
3. **"No account can read it" is known.** The default login falls back to gh's active account even when that account
   cannot read the repository. The link state therefore runs the existing `canRead` probe on the login it would use,
   once per repository and launch, and `GHL-01` disables the item with the reason.
4. **Attachments are written by RockyKit.** `LinkAttachments` (RockyKit) renders `GHL-04`/`GHL-05`'s exact Markdown for
   an issue, a PR and a branch. It writes the file under `~/Library/Caches/Rocky/Pasted/<UUID>/<name>`, through a
   general writer that `PastedAttachments`' PNG path also uses. The chip is the file attachment.
   - `FileBadgeLook` picks the GitHub, PR or branch mark from the name's prefix (`[GITHUB]-`, `[GITHUB]-PR-`,
     `[BRANCH]-`), and its tooltip is the issue's or branch's title.
   - The transcript and ↑ history get the mark for free, because the path carries the prefix.
5. **Switching is one `AppModel` operation.** `switchWorktree(workspaceId:to:)` takes `.branch(local|remote)` or
   `.pullRequest(number)` and works in this order:
   1. It checks `GHL-05`'s preconditions at pick time: `GitBranchService.status` read directly (`uncommitted == 0`,
      `commitsAheadOfBase == 0`), `unsavedEditors` empty, and the branch not held by another worktree.
   2. It switches (`git switch`, `--track` for a remote branch, the PR's head fetched first).
   3. It updates the workspace record's `branch` and `baseRef` (a PR's is `origin/<baseRefName>`) through
      `RockyStore.update`, and reloads the workspace.
   4. It deletes the old empty `rocky/<city>` with `git branch -D`. `-d` refuses when the new HEAD does not contain it;
      it was just proven empty, so this is the user's decision of 2026-09-25.
   5. It refreshes the PR panel with `.action`.
   
   New processes then get the new `ROCKY_DEFAULT_BRANCH`. A failure leaves the worktree and the record unchanged and
   says why.
6. **The issue's title names the workspace from the attachment.**
   - `titleIfNeeded` receives the message's attachments.
   - When the first message carries a `[GITHUB]-<n>.md`, the title is that file's first line, `# #N Title`, without the
     `# `. It is read at send time, while the file exists.
   - `ChatSessionRecord.title`'s 40-character cut applies as today.
   - A message whose text is empty and has no issue leaves the conversation untitled. This fixes today's `""` title.
   
   The title names the conversation too, and so the sidebar row (`conversationTitles`).
7. **Tasks run in their own tabs, without changing `PTYSession`.** A task's tab is a `PTYSession` titled with the
   task's label.
   - `TSK-03`'s "dedicated" means the same label reuses its tab once that process ended: the tab is replaced by a new
     session in the same place, and the selection follows.
   - "new" opens a new tab each run.
   - "shared" reuses one "Task" tab, whose title is the task running in it.
   - The echo line and `clear` go through the command that starts the task: `clear;`, and `printf` of the command
     before it. No local write into the PTY.
   - A task tab can close, like a terminal tab.
8. **Background waits read the PTY's output.** `TaskOutputWatcher` (RockyKit, pure) takes byte chunks and returns lines
   with ANSI escapes removed, and it matches `beginsPattern`/`endsPattern`. The runner attaches it before the session
   starts, so no output is missed.
9. **The runner is testable without a real shell.** `TaskRunner` (RockyKit) takes a launcher protocol, which is a PTY
   session in the app and a fake in tests. The graph, inputs, waits and stop rules are unit tested, with one real
   `/bin/zsh` test for the wiring.
10. **The Run script mode stays as it is today.** `TSK-03` says a non-concurrent task stops the others "in that
    repository, as the Run script does today". Today's loop stops every workspace's Run script in every repository,
    and tasks do the same, so both keep one rule. Tell the designer.
11. **The input pickers are Rocky's menus with keys.** `MenuPresenter` gains ↑/↓, Return on the highlighted row, a
    highlighted default, and an `onCancel` when it closes without a pick. `TSK-04`'s pickString is such a menu above
    Run, and promptString is a small field in a mini-modal (`DLG`).
12. **A reveal from the model is a request.** Starting a task from Run, or Show in a toast, selects its tab and unfolds
    the panel through `AppModel.terminalRevealRequests[workspaceId]` (session id and serial). `WorkspaceDetailView`
    acts on it, as it does on `requestTerminalToggle`. `AppModel.onToast` gains an optional action.

### Task 9: The kit (WSC-01, WSC-04, WSC-05, WSC-06, KIT-18)

- **The worktree without hooks.** `WorktreeService.create` runs `git -c core.hooksPath=/dev/null worktree add …`, so
  no hook runs and it returns after the fetch and the checkout. Retry reuses an existing `rocky/<name>`, running
  `worktree add` without `-b`.
- **The hook, found and run.** `postCheckoutHook(worktree:)` is `git rev-parse --git-path hooks/post-checkout` in the
  worktree, which honors `core.hooksPath`, and it is used only when it exists and is executable. The hook runs as the
  Setup tab's first step, with git's arguments `0000…0000 <HEAD> 1`, the worktree as its working directory and
  ENV-01's environment. Then rocky.json's Setup script runs in the same tab, each step opening with its line and
  closing with its end line (`WSC-05`). A failing step stops the next one.
- **One creation per repository** (`WSC-01`). `AppModel.creatingWorkspaces[repoId]` is set on the same main-actor turn
  as the call, before any await. A second call while one is in flight does nothing. The "+", ⌘N and New Workspace read
  it. Only the git part blocks; a Setup that is still running does not.
- **The workspace before its worktree** (`WSC-03`). The workspace exists in memory from the call on, selected, with its
  name and branch. It is saved with its port once the worktree exists, and its first conversation (CNV-02's agent) is
  ready at once. A message sent meanwhile waits and goes when the agent is ready.
- **The statuses** (`WSC-02`). `WorkspaceStatus` gains `creating` and `creationFailed` (before `needsYou`) and
  `settingUp` (right after `working`), with their tooltip texts. `busyMessage` "Creating workspace…" goes.
- **Failure, Retry and Remove** (`WSC-06`).
  - A failure keeps the workspace in memory as failed, with git's message.
  - Retry reruns the creation with the same name.
  - Remove, and Remove while creating (which stops git first), deletes the half-made folder, runs `worktree prune`
    and deletes the branch if the attempt made it.
  - A quit during a creation stops git and cleans up the same way.
- **A failed fetch** stays non-fatal and becomes a toast.
- Tests: `KIT-18`'s list, on a temporary repository with a hook that writes a file.
  - `create` runs no hook.
  - `postCheckoutHook` finds the hook through `core.hooksPath` and skips a non-executable one.
  - A second `createWorkspace` while one is in flight does nothing.
  - Retry reuses the branch.
  - The cleanup removes the folder and the empty branch.
  - The Setup tab runs the hook and then the script, and a failing hook stops the script.
  - `WorkspaceStatus` keeps its order with the new states.

## Part D: Removing a workspace (WSC-07, KIT-19), added 2026-09-28

> Added by the user's report of 2026-09-28, on removing a workspace: "cuando remuevo un worktree se ve esto durante
> unos segundos y luego aparece algo de git branch fatal no sé qué y luego sí se borra". Read `WSC-07` and `KIT-19` in
> the M2.9 HTML, and M2.8's `DLG-01` row for Remove.

**Cause (in `AppModel.removeWorkspace`):**
- The workspace stays selected, and its FileWatcher and PR refreshes keep running while `git worktree remove`
  deletes its files. Changes then lists them as "D", and a git status read inside the half-deleted worktree fails
  with "fatal:", which Rocky shows.
- `stopChats` runs first, so the view looks for a conversation that is gone ("Opening the conversation…").
- The removal takes seconds, because it also deletes node_modules.

## Part E: Child processes inherit nothing of Rocky's, added 2026-09-28

> Added by user decision, 2026-09-28 ("sí, agrégalo a M2.9"), for a known issue carried since M2.7: terminal shells
> inherit every open file descriptor of Rocky.

**What happens (checked in the code, 2026-09-28):**
- `PTYSession.start()` uses SwiftTerm 1.20.0's `LocalProcess.startProcess`. Its swift-subprocess path is compiled out
  (`LocalProcess.swift:12`, `#if false //canImport(Subprocess)`), so it takes `startProcessWithForkpty`: `forkpty`,
  then `execve` (`Pty.swift:97-106`).
- A descriptor without `FD_CLOEXEC` survives `execve`. So every terminal, script and task gets Rocky's open files: the
  SQLite database, the pipes of each agent's ACP connection, and the other PTYs' masters.
- A child that outlives its tab keeps them all open, for example `redis-server --daemonize yes`, which celes-platform's
  tasks start. An agent whose pipe Rocky closes may then never see its end, and keep running.
- Foundation's `Process` (git through `ProcessRunner`, the agents' launch) may or may not close them. The test below
  settles it for each path.

### Task 13: Close Rocky's descriptors in every child

- **A test first**, in `Tests/RockyKitTests`.
  - The test process opens a canary descriptor with no `FD_CLOEXEC`, a pipe. It then starts, through each path Rocky
    uses, a child that lists its open descriptors (for example `/bin/ls /dev/fd`, or `lsof -p $$`):
    - a `PTYSession` terminal;
    - a script;
    - `ProcessRunner` (git);
    - an agent launch (the ACP connection's process).
  - Each child must see only 0, 1, 2 (and what its own listing opens), and never the canary. The test fails today for
    the PTY path.
- **The fix:** right before each spawn, mark every descriptor of Rocky's from 3 up as close-on-exec. A helper in
  RockyKit sets `FD_CLOEXEC` on each open descriptor, `fcntl(F_SETFD)`, read from `/dev/fd` or `proc_pidinfo`. It is
  called by `PTYSession.start()` before `startProcess`, and by any other spawn path the test shows to leak.
  - The child's own stdin, stdout and stderr are dup2'd by forkpty or by `Process`, so they stay open.
  - Rocky's own use of its descriptors does not change, because `FD_CLOEXEC` only acts at `execve`.
  - A descriptor another thread opens between the marking and the fork can still leak. The window is tiny; say so
    in the comment.
- **Docs:** `m2.9-verification.md` and the known-issues lists lose the "terminals inherit every descriptor" line.
  `docs/README.md` has nothing to change unless it mentions the issue.
- Then build once, and run `swift test` twice in parallel and once `--no-parallel` over the whole branch. Record the
  counts.

## Known risks

- GitHub's search limit is 30 requests a minute. The debounce keeps typing under it, and a rate-limit error shows as
  the picker's error.
- `git switch` to a PR's head needs `refs/pull/<n>/head` fetched, or the head branch when it is in the same repository.
  Fork PRs are out (`OUT-50`).
- The Markdown files live in `~/Library/Caches`, which macOS may clear. The transcript's chip then opens nothing, which
  is the same as pasted images today.
- celes-platform's tasks hard-code ports 8000 and 6379. Two workspaces running them at once collide; that is why the
  Run script mode stops the others (Decision 10).
